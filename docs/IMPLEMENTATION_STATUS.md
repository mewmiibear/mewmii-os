## Deferred V3 findings

Surfaced during the V2 Operational Workflow pass and **deliberately not fixed** — each is either a real behaviour change needing its own audit/approval cycle, or would have required duplicating logic that V2's constraints ruled out. Recorded here so none is lost. **None is scheduled or approved.** No V3 work has begun.

| Finding | Severity | Detail |
|---|---|---|
| `product_cost_history` `ON DELETE CASCADE` | **High — silent historical data loss** | The FK from `product_cost_history.supplier_order_item_id` cascades, so removing a PO line destroys the frozen landed-cost snapshots taken at receiving. Exposed by a Reverse Receiving test whose assertion failed for the wrong reason and revealed the real path. These snapshots are the historical costing record — once gone they cannot be recomputed, because they froze inputs that have since changed. Fixing it is a schema change (`ON DELETE SET NULL` plus a nullable column, or a soft-delete) and needs a migration, so explicitly out of V2 scope |
| `customer_storage_remove()` guard location | Medium | The "cannot remove units already committed to an open ship request" rule lives in `modules/customer-storage/view.php`, not inside `customer_storage_remove()` which performs the write. Safe **today** — grep confirms view.php is its only caller — so there is no live bug. But the rule is enforced by location rather than by the function owning the mutation, so any future caller (CLI cleanup, bulk tool, API endpoint) would silently bypass it and could strip units already promised to a customer |
| Supplier order receiving status duplication | Low–Medium | "Outstanding" is defined twice: `modules/supplier-orders/index.php` computes it **per order** via `supplier_orders_outstanding_batch()`, while `modules/supplier-orders/view.php` gates its receive form **per line** via `$hasOutstandingLines`. They diverge only if one line is over-received while another is short — unreachable through normal flow, since `supplier_order_receive_item()` caps at remaining. Reconciling them would mean either a third definition or changing one of the two, so P7 matched the existing list-side number rather than introducing a new one |
| Cancelled PO receiving form inconsistency | Low | `view.php` does not gate its receive form on status, so a cancelled order with outstanding lines still renders it; `index.php` forces `units_outstanding` to 0 for cancelled orders, so no Receive shortcut appears. The mismatch fails safe (shortcut hidden while the page still allows receiving), but the detail page arguably should not offer receiving on a cancelled order at all. That is a receiving **behaviour** change and needs its own approval |
| N+1 availability queries | Low — performance | `modules/ship-my-box/create.php` and `modules/customer-storage/view.php` call `ship_request_storage_lot_available()` once per lot (~2 queries each), on top of the pre-existing per-lot `variation_build_label()`. Roughly 3 queries per stored lot. Acceptable today because customer storage per customer is small, and a batched variant was **rejected** during V2 because it would have duplicated the helper's logic — the very thing the pass was avoiding. Revisit only if a customer accumulates many lots |
| Minor naming / title inconsistencies | Cosmetic | (a) `$appTitle` is set by every module page but never rendered — `<title>` emits a bare `Mewmii OS` sitewide. Pre-existing, unrelated to V2, noticed during the rename. (b) The dashboard quick-action button still reads "Allocate Preorders" while the page is now "Allocation Center"; left deliberately because it pairs with "Reserve Waiting Orders" as a verb phrase. Renaming it would mean renaming both buttons, which is a wording decision, not a defect |
